# Design

## Context

`MacroEngine` читает ORM-связь плана по позиции и каждый раз заново получает HTTP-данные. Сериализованная тренировка содержит `exercise_instances[].exercise_list_id`. Владелец экземпляра и подхода — workouts-service. Его PUT экземпляра принимает метаданные, запись списка подходов через этот PUT невозможна. Начало сессии уже блокирует строку Workout. В применённом плане хранятся идентификаторы максимумов, но отсутствуют настройки округления из запроса применения.

## Goals / Non-Goals

Единица подтверждения — пакет трёх видов изменений подходов одного применённого плана. Гарантия атомарности включает все затронутые тренировки этого пакета. Вставка мезоцикла имеет отдельные эффекты в двух сервисах. Её результат в смешанном preview должен быть различим, подтверждение пакета подходов не должно попутно запускать вставку.

## Decisions

### Входные данные и отбор

Plans нормализует один ответ workouts на границе транспорта. Данные определения упражнения служат фильтру, для записи используется цепочка workout → instance → set. Явный фильтр с нулём совпадений даёт пустой результат, ошибки каталога завершают вычисление. При выборе по тегам учесть пагинацию definitions, включая совпадение на следующей странице. У всех трёх действий один этап отбора до вычисления. Валидировать также сохранённый DSL, указать id ошибочного правила.

Для послесессионной подсказки закрепить тренировку-наблюдение и окно целей до продвижения индекса. Ручной preview показывает источник и цели. Для оконных условий загружать требуемые наблюдения в одном исполнении. Факт выполнения относится к отмеченному подходу сессии. Для дельты нужен идентифицируемый исходный плановый подход и фактический результат. Отсутствие достоверной пары на старых данных показать явно. Двойное чтение текущего экземпляра и сопоставление по номеру в списке создают ложную нулевую дельту.

### Вычисление (DATA)

Новый расчёт принимает снимок подхода и типизированное намерение. Отдельно разбирать целые изменения повторений/подходов, проценты со знаком и целевой RPE. Для старых JSON сохранить значение процентов как записано. По величине 0.90 невозможно определить намерение автора. Согласовать AI-подсказку с Flutter, проверить реальную подстановку упражнения в промпт и валидацию полученного JSON.

| Действие | Что фиксирует пользователь | Что нужно проверить в результате |
| --- | --- | --- |
| Нагрузка до RPE | Повторы и целевой RPE | Из точных вариантов сохранить текущую интенсивность, если допустима. Иначе выбрать ближайшую к исходной, задать стабильное разрешение равенства. Рассчитать вес из эффективного 1ПМ и шага. |
| Повторы до RPE | Интенсивность и целевой RPE | Вычислить повторы, сохранить интенсивность и соответствующий ей рабочий вес. |
| Нагрузка в процентах | Знак и относительное изменение, исходные повторы | Проверить допустимость результата для заданного типа подхода и пересчитать зависимые поля один раз. |
| Изменение повторов | Целочисленное смещение при сохранённой нагрузке | Проверить итоговое число повторений и его согласованность с остальными полями. |
| Изменение числа подходов | Число и порядок подходов | Клонировать полный последний подход с новыми идентификаторами или удалять с конца. Сохранить порядок, тип и вложенные части. |

Изменения составного подхода работают с его эффективными частями. При недостатке данных исполнитель указывает упражнение, подход и отсутствующее поле. Для новых тренировок сохранять эффективные максимумы упражнений, шаг и режим округления на связи AppliedPlanWorkout во время материализации. Нормализация микроцикла меняет максимум следующей тренировки. Привязка к workout id сохраняется при перестановке и вставке тренировок. У старого плана сначала искать достоверный источник исходных настроек, запросить недостающие данные до вычисления зависимого веса. Гадание шага по сохранённому весу создаёт необратимую неоднозначность. Владелец выбрал предложение ближайшего допустимого варианта в preview. При смещении повторов ранжировать по отклонению от запрошенных повторов, затем по отклонению от исходной интенсивности. При процентном изменении сохранять повторы, затем минимизировать отклонение от запрошенной интенсивности. При целевом RPE сначала минимизировать отклонение от RPE. Остаточные равенства разрешать по близости к исходным полям и стабильному порядку значений. Показывать запрос и полное предложение до подтверждения.

### Preview, исполнение и повтор (EXEC, ACCESS, READY)

Вычислить правила по существующему порядку priority, id на одной рабочей копии. Следующее действие получает результат предыдущего. Сохранять серверный preview с непрозрачным id, владельцем, планом, перечнем целевых экземпляров, исходными и итоговыми значениями. Для вложенных добавлений сохранить локальную идентичность до назначения DB id. Клиент передаёт только id. Задача и синхронный API используют один обработчик. Публичный клиент не может заменить исходные данные или передать новое содержимое записи с этим id.

Передавать подготовленный пакет владельцу данных по аутентифицированной межсервисной границе. Исполнитель проверяет владельца плана и каждого workout/instance/set и сохраняет результат в той же транзакции, что и изменения. Блокировать целевые тренировки в стабильном порядке, проверить состояние сессии и исходные значения под блокировкой. Согласовать с конкурентными изменениями подходов и их состава через защиту строк/версии. Уникальный ключ выполнения и проверка содержимого команды отличают повтор подтверждения от нового preview. После commit инвалидировать затронутые ключи кеша и проверить пользовательский GET. Утерянный ответ после commit восстанавливается по записанному результату операции.

Временный отказ чтения тренировок, каталога для тегов или необходимой RPE-таблицы даёт ошибку зависимости и допускает новый preview после восстановления. Для операции клонирования готового подхода доступность RPE не нужна. После отказа во время записи повторять тот же подтверждённый id. При генерации workouts получает части составного подхода в одном наборе. Публичный GET деталей в gateway читает HTTP-представление владельца данных и добавляет клиентские имена полей, включая вложенные части. В ранее разложенных подходах утраченная группировка автоматически не восстанавливается. Отдельного доменного события не вводится. Для существующей доставки задания Celery проверить повтор и восстановление результата.

## Risks / Trade-offs

- Загрузка сохранённого правила старой версии → проверить fixtures старых JSON без миграции чисел по эвристике.
- Редактирование тренировки между чтением и подтверждением → сравнить под блокировкой, вернуть конфликт с предложением обновить просмотр.
- Два экрана Flutter и подсказка завершённой сессии работают через разные вызовы → проверить каждый, включая ошибку в ответе и повтор после таймаута.
- Серверный снимок и журнал выполнения требуют хранилища → миграции выпускаются раньше клиентов. Ограничение времени жизни снимка не должно позволять уже выполненной команде исполниться повторно.

## Migration Plan

1. Выпустить добавочные схемы хранения настроек и результатов, внутренний обработчик workouts, затем plans и worker с поддержкой новой версии контракта. Старый клиент без id получает явный ответ о необходимости предпросмотра; эту комбинацию проверить отдельно.
2. Обновить Flutter и подсказку сессии. Новому клиенту со старым сервером без идентификатора preview запретить подтверждение вычисленных подходов и показать причину. Оба режима записи одновременно для одного подтверждения недопустимы.
3. При откате клиента/worker сохранить данные выполненных команд. Направлять повторы к совместимому обработчику или вернуть явную временную недоступность. Возврат к прежней версии не обращает уже подтверждённые изменения тренировок.

## Дополнение после анализа сочетаний

Согласованный в чате подход реализуется через неизменяемые типы значений подхода и настроек веса, типизированные действия и единый проверяемый переход. На транспортной границе остаются JSON-адаптеры. Конструктор проверяет конечность, диапазоны и согласованность алиасов. Каждая операция проверяет исходное состояние и полученный результат. Исторические неполные подходы можно клонировать после структурной проверки, для математического преобразования нужны интенсивность и повторы. При известном максимуме несовпадение веса с расчётом даёт явную ошибку с адресом подхода. Отрицательные веса отклоняются.

Числовой бюджет первой реализации — целое смещение повторов или подходов от -100 до 100 одним действием, до 1000 подходов или частей в одном экземпляре. Это выбранные технические пределы, они защищают вычисление и клонирование от неограниченного расхода памяти. Целые смещения разбираются через Decimal без потери точности.

Total_Reps завершённой сессии использует сохранённые фактические значения отмеченных подходов. При отсутствии сессионного снимка для исторических или плановых данных используется текущее представление. Один составной подход считается одним элементом holds_for_sets, условие должно выполняться для всех его частей. Оконные условия используют последние N завершённых наблюдений, пропуски не включаются в окно. Дельта частей сравнивается только при неизменной структуре.

Для изменения подходов ключ срабатывания состоит из macro id, хеша нормализованного правила, id тренировки-наблюдения и id целевой тренировки. Квитанция срабатывания записывается в транзакции workouts. Новый preview пропускает уже выполненные правила, конкурирующие preview с одинаковыми ключами дают конфликт. Повтор того же preview возвращает сохранённый результат. Исторические квитанции без ключей продолжают поддерживать повтор по preview id.

Обычный редактор и макросы блокируют workout перед instance и set. Результат чтения для записи обновляется после ожидания блокировки. Структурная проверка выполняется перед записью. Конкурентные запросы проверяются на PostgreSQL.

Послесессионный worker повторно использует сохранённый preview. Продвижение индекса получает observation_workout_id и фиксирует session_advanced на связи плана с тренировкой под блокировкой плана в одной транзакции. Прежний вызов advance без observation_workout_id сохраняет ручное смещение. Эти гарантии относятся к изменениям подходов и продвижению индекса, жизненный цикл внешних эффектов вставки мезоцикла остаётся отдельным.

Снимок завершения также сохраняет macro_completed и macro_metrics, поэтому поздние изменения отметок или готовности не меняют наблюдение. Идентификаторы частей назначаются в workouts при старте сессии, перенос идентичности через клиентские изменения контролируется при вычислении дельты. Историческая составная дельта без идентификаторов явно отклоняется.
